# 排障指南

先区分“能发现设备”“通道可用”和“消息已送达”。状态规则见 [通信架构](arch.md)。

## 收集信息

1. 在双方设备复现一次，记录时间、应用版本、网络环境与联系人。
2. 从聊天的连接日志导出对应记录，再检查全部日志中的启动、休眠和发现事件。
3. 按时间、联系人和消息 ID 对照双方日志；展开源日志查看地址、传输类型和原始错误。

日志仅存本机，不自动上传；保留最多 2000 条、7 天、约 3 MiB。不记录聊天正文或附件内容，凭证会脱敏。浏览器日志不包含另一台设备或服务器的日志。

## 按现象定位

| 现象 | 优先检查 |
| --- | --- |
| 找不到对方 | 双方是否上线、发现方式和服务器是否可用；局域网是否隔离；蜂鸟号及目标 UUID 是否匹配 |
| 列表有对方，TCP 建连超时 | 双方地址、VPN 路由和防火墙入站规则；mDNS 可发现不代表 TCP 端口可达 |
| 收到连接请求，但回连失败 | 回连方向的地址、端口和入站权限 |
| `Stale peer session` / `Peer session changed` | 对端是否重启，发现记录是否仍指向旧实例 |
| TCP、WebRTC 都失败 | 网络是否允许直连；需要中转时，确认同一服务器支持且双方都允许 |
| 连续 3 个探测周期后显示离线 | 是否既无有效 pong，也无消息、ack 或其他响应；检查休眠、网络切换及双方重连记录 |
| 没有 pong，但消息仍正常收发 | 可能是旧客户端；有效收发会清零失败次数，不应仅因缺少 pong 离线 |
| pong 正常，消息却未送达 | 按消息 ID 检查接收、保存和 ack；关注磁盘空间、目录权限与传输超时 |

离线提示不阻止发送；无可用通道或缺少接收确认时，会保留失败记录，不会由服务器代收。

## 调整检查间隔

`VITE_PEER_CHECK_INTERVAL_MS` 控制非当前聊天的后台检查，默认 `10000` 毫秒，允许 `1000`–`300000`。在 `.env.json` 对应环境的 `ssg` 配置中修改后运行 `npm run init`；开发服务需重启，部署资源和安装包需重新构建。当前聊天仍每 10 秒检查。

自动测试覆盖状态与收发逻辑；跨系统防火墙、VPN 和真实局域网问题仍需双机日志确认。
